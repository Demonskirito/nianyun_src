# 图容量治理评估（阶段 5）

> 只出评估与设计，不含实现。明确不与阶段 1/2 同包部署。
> 数据来源：会话 `1dd9ded9ed239711` 在第 6761 条事件时的 checkpoint 快照（2026-11-07）。

## 1. 现状数据

| 指标 | 数值 |
|---|---|
| 节点上限 `MAX_NODES` | 500 |
| 当前节点 | 500（已封顶） |
| 当前边 | 464 |
| 历史累计淘汰 | 130 |
| 累计新建 | 630（= 500 + 130） |
| 工具调用次数 | 306 |
| 平均每次调用新增节点 | ≈ 2.06 |
| 节点构成 | endpoint 478 / parameter 17 / asset 4 / identity 1 |
| 状态构成 | untested 480 / blocked 15 / testing 5 |
| 图 JSON 体积 | 342 KB（≈ 700 B/节点） |
| checkpoint 总体积 | 1001 KB（图占 34%，其余是任务簿、事件投影、审查记录） |

**结论**：这个资产在 306 次工具调用内就把 500 个节点撑满，之后每新增一个节点就淘汰一个。
"挖得越深越好"在当前配置下被容量反复截断——不是策略问题，是容量问题。

## 2. 增长曲线外推

按 2.06 节点/次工具调用、单资产会话常见 300–800 次调用估算：

| 工具调用 | 新建节点（累计） | 500 上限下被淘汰 |
|---|---|---|
| 306（当前） | 630 | 130 |
| 500 | ~1030 | ~530 |
| 800 | ~1650 | ~1150 |

也就是说：一个中等规模资产跑到底，**约 70% 的发现会被淘汰**。
淘汰不是"删了垃圾"——现在被删的多数是 `untested`（还没打过），这正是最该保留的那一批。

## 3. 方案 A：提高上限

### 做法
把 `MAX_NODES` 从 500 提到 1500（或按会话规模自适应），其余不变。

### 容量与成本

| 项 | 500（现状） | 1500 | 2000 |
|---|---|---|---|
| 图 JSON | 342 KB | ~1.0 MB | ~1.4 MB |
| checkpoint | 1.0 MB | ~1.7 MB | ~2.1 MB |
| CAS 指纹计算（每次 merge） | 5–10 ms | 15–30 ms | 20–40 ms |
| 图渲染（DFS/分量/寻路） | 毫秒级 | 毫秒级 | 10–30 ms |
| 实现成本 | — | 改 1 个常量 + 回归 | 同左 |

### 风险
- checkpoint 随会话写入数据库，体积增长会放大每次 CAS 的序列化开销；
- 上下文投影（`serialize`/`graphContextView`）若不截断，会把上千节点塞进 prompt；
- 前端历程图节点上千时布局耗时上升（需实测）。

### 收益
- 直接消除抖动，一行改动、零结构风险；
- 对"已挖 478 端点"的资产立竿见影。

## 4. 方案 B：冷节点旁路存档

### 冷节点判定
按"保留价值"三档，只有最低两档可归档：

| 档 | 判据 | 处理 |
|---|---|---|
| 热 | `status = testing` / 被 active 假设引用 / 最近 20 轮更新过 | 永远留在主图 |
| 温 | `status = untested` 且 `origin = discovery`（从 sitemap/JS 摘出、从没真打过） | 超过 30 轮未更新才归档 |
| 冷 | `status = dead_end` 且 `hits > 0`（打过多次判死） | 超过 10 轮未更新即可归档 |

`vulnerable` / `identity` / `asset` / `blocked`（被墙）不归档。

### 存档格式
按会话 + host 分片，JSONL 追加写：

```
data/graph-archive/<session_id>/<host>.jsonl
{ "id": "ep:developer.aliyun.com/ask/{id}", "type": "endpoint", "status": "dead_end",
  "depth": 3, "properties": {...}, "incident_edges": [...], "archived_at": 1794..., "reason": "cold" }
```

只存节点本体与它的邻接边描述，不存全图，便于按需回捞。

### 回捞路径
三个触发点：
1. **假设重新点名**：`deriveHypotheses` 产出的节点不在主图 → 按 host 加载对应分片；
2. **寻路目标命中**：`planRoutes` 的目标在归档里 → 回捞一跳邻域（目标 + 直接邻居）；
3. **人工指定**：Desk 上点"回捞该 host"。

回捞后节点标 `archived: true`，主图只保留它的轻量卡片（id + status + note），邻接边按需展开。

### 成本
- 新增 I/O 与索引维护（每会话一个目录，按 host 分片）；
- 状态一致性：归档节点被假设引用时要么回捞、要么让假设失效，需明确优先级；
- 实现量明显大于方案 A（预计 300–500 行 + 迁移脚本 + 回归）。

### 收益
- 主图常驻内存可控（如固定 500 热点），同时不丢发现；
- 真正解决"挖得深就必然截断"的结构问题。

## 5. 对比与建议

| 维度 | A（提高上限） | B（旁路存档） |
|---|---|---|
| 解决抖动 | 是（延后） | 是（结构性） |
| 实现成本 | 极低 | 高 |
| 风险 | 体积/CAS 开销线性上升 | 状态一致性、回捞正确性 |
| 适用规模 | 单会话 ≤ 1500 节点 | 无上限 |
| 建议节奏 | **先做** | 二期 |

**建议**：先做 A 的温和版本（`MAX_NODES` 500 → 1500），同时给 `graphContextView` 加硬截断（只投影前 N 个高价值节点），用一轮实跑看 CAS 耗时与渲染耗时是否可接受。
若后续出现"单会话 1500 也不够"的真实案例，再启动 B，并按上文三档判定与回捞路径做设计评审。

## 6. 与阶段 1/2 的关系

阶段 1 解决的是"容量满时不要崩、不要记错账"，阶段 2 解决的是"满了该淘汰谁"。
本评估解决的是"根本不该这么早满"。三者独立，可分开部署；本阶段只给结论，不含代码。
